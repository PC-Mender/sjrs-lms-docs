## Overview

This document explains how version management, GitHub releases, and notifications work together in the SJRS LMS release workflow. The app uses a custom `version-prepare.js` script for versioning, GitHub Actions CI for automated releases, and optional notification scripts for deployment alerts.

---

## Complete Workflow

### Step-by-Step Process

There are two paths to a release:

#### Path 1: Local Release (Developer-Initiated)

```
1. Developer commits changes using conventional commit format
   ↓
2. Developer runs: npm run version:prepare
   ↓
3. Script analyzes commits since last tag, determines version bump type
   ↓
4. Version bumped in package.json
   ↓
5. CHANGELOG.md updated (all relevant commits grouped by section)
   ↓
6. Version changes committed: chore(release): bump version to X.Y.Z [skip ci]
   ↓
7. Git tag created (vX.Y.Z)
   ↓
8. Quality gates run locally (fail fast before push)
   ↓
9. Commits and tag pushed to GitHub
   ↓
10. GitHub Actions CI triggers on branch push
   ↓
11. CI: quality-gates → build → test-frontend (4 shards) → release → github-release
   ↓
12. GitHub Release created (changelog extracted from CHANGELOG.md)
   ↓
13. Developer deploys manually: npm run deploy:production
   ↓
14. (Optional) Developer sends notification: npm run notify-deployment
```

#### Path 2: CI-Initiated Release (Automatic on push to main)

```
1. Developer pushes commits to main branch
   ↓
2. GitHub Actions CI triggers automatically
   ↓
3. CI runs: quality-gates → build → test-frontend (4 shards)
   ↓
4. release job: runs version-prepare.js (with --skip.tag --skip.commit)
   ↓
5. If version changed: commits + creates tag + pushes
   ↓
6. github-release job: creates GitHub Release from CHANGELOG.md
```

:::note
Deployment to Cloudflare Workers is **manual** — there is no automatic deploy step in CI. Use `npm run deploy:production` (or `npm run deploy:staging`) after the release is created.
:::

### CI Workflow Structure

The CI workflow (`.github/workflows/ci.yml`) has these jobs:

| Job | Description | Runs on |
|-----|-------------|---------|
| `quality-gates` | Type check (strict), backend tests, quality gates, security audit, route security manifest | All pushes/PRs |
| `build` | Production build (tsc + Vite), bundle size validation | All pushes/PRs |
| `test-frontend` | Frontend tests (4 shards) | All pushes/PRs |
| `release` | Version bump, tag, changelog | `main` branch or `workflow_dispatch` only; skips bot commits and `chore(release):` commits |
| `github-release` | Create GitHub Release from CHANGELOG.md | Only if `release` job created a new tag |

A separate `security.yml` workflow runs Gitleaks secret scanning and SBOM + license checks on `main` branch pushes.

:::note
The `release` job uses Node 22 and sets `HUSKY: 0` to skip git hooks during CI. Concurrency groups prevent overlapping runs for the same branch.
:::

## Version Consistency

### How Version Stays Consistent

**Three places where version must match:**

1. **package.json** - `"version": "8.2.2"`
2. **Git Tag** - `v8.2.2`
3. **GitHub Release** - Release `v8.2.2`

### Version Verification in CI

The CI `release` job compares the previous git tag with the new version from `package.json` after running `version-prepare.js`. If the version changed, it commits, creates a tag, and pushes. If unchanged (no conventional commits since last release), it skips the release.

```yaml
# In ci.yml — release job
- name: Run version prepare
  run: |
    npm run release -- --skip.tag --skip.commit
    new_version=$(node -p "require('./package.json').version")

- name: Check if version changed
  run: |
    current_version_num=$(echo "$current_version" | sed 's/^v//')
    if [ "$current_version_num" != "$new_version" ] && [ -n "$new_version" ]; then
      echo "version_changed=true"
    else
      echo "version_changed=false"
    fi
```

The `version-prepare.js` script also checks locally whether a tag already exists before creating one:

```javascript
// In version-prepare.js
function verifyVersionConsistency(newVersion) {
  const existingTag = `v${newVersion}`;
  try {
    execSync(`git rev-parse ${existingTag}`, { stdio: 'ignore' });
    console.warn(`Tag ${existingTag} already exists. Skipping tag creation.`);
    return false;
  } catch {
    return true; // Tag doesn't exist, good to go
  }
}
```

## Commit Type Analysis

### How Commit Types Are Analyzed

The `version-prepare.js` script analyzes all commits since the last tag to determine the version bump type. It picks the **highest-priority** bump type across all relevant commits.

#### Version Bump Rules

```bash
# From commit messages:
feat: add new feature        → Minor bump (8.2.2 → 8.3.0)
fix: resolve bug            → Patch bump (8.2.2 → 8.2.3)
BREAKING CHANGE: major      → Major bump (8.2.2 → 9.0.0)
breaking: major change      → Major bump (8.2.2 → 9.0.0)

# Also treated as patch bumps:
perf: optimize query        → Patch bump (8.2.2 → 8.2.3)
refactor: cleanup code      → Patch bump (8.2.2 → 8.2.3)
docs: update readme         → Patch bump (8.2.2 → 8.2.3)
style: format code          → Patch bump (8.2.2 → 8.2.3)
test: add unit tests        → Patch bump (8.2.2 → 8.2.3)
ci: update workflow         → Patch bump (8.2.2 → 8.2.3)
build: update deps          → Patch bump (8.2.2 → 8.2.3)
revert: rollback change     → Patch bump (8.2.2 → 8.2.3)
chore: update config        → Patch bump (8.2.2 → 8.2.3)
```

:::note
Commits with `bump version` or `[skip ci]` in the message are **skipped** during analysis. If no conventional commit is found since the last tag, the script exits without creating a release.
:::

#### Changelog Section Grouping

Commits are grouped into changelog sections by the `classifyCommit()` function in `version-prepare.js`:

| Commit Prefix | Changelog Section | Emoji |
|---------------|-------------------|-------|
| `feat:`, `add:` | Added | ✅ |
| `fix:`, `bug:` | Fixed | 🐛 |
| `breaking:` / `BREAKING CHANGE:` | Changed | 💥 |
| `chore:`, `refactor:`, `docs:`, `style:`, `test:`, `ci:`, `build:`, `perf:` | Technical | 🔧 |

#### File-Based Analysis (auto-version.js only)

The `auto-version.js` script can infer commit type from changed file paths when no commit message is available:

```javascript
// From file paths:
src/components/...          → ui scope → feat (minor version)
functions/api/...          → api scope → feat (minor version)
docs/...                   → docs scope → docs (patch version)
scripts/...                 → config scope → chore (patch version)
```

## GitHub Releases

### Automatic Release Creation

The `github-release` job in CI runs **only if the `release` job created a new tag**. It:

1. **Extracts release notes** from `CHANGELOG.md` by finding the section matching the new version
2. **Creates or updates a GitHub Release** using `gh release create` / `gh release edit`
3. Uses the tag (e.g., `v8.2.2`) as the release title

:::note
The release notes come directly from `CHANGELOG.md` — no deployment URL, status, or commit SHA is included. The `CHANGELOG.md` is updated by `version-prepare.js` which groups all relevant commits into sections (Added, Fixed, Changed, Technical).
:::

### Release Notes Format

The notes are extracted by an `awk` script that finds the matching version section in `CHANGELOG.md`:

```markdown
## [8.2.2] - 2026-07-29

### Added
- ✅ New analytics dashboard

### Fixed
- 🐛 Login redirect issue

### Technical
- 🔧 Refactored API middleware
```

If the changelog section is empty or not found, the release notes default to: `See CHANGELOG.md for details.`

## Notifications to Database

### Overview

Notifications are **not sent automatically by CI**. There are two scripts that can send deployment notifications:

1. **`notify-deployment.js`** (`npm run notify-deployment`) — Standalone script, run manually after deployment. Reads version from `package.json`, extracts changelog info, and sends a detailed notification.

2. **`auto-version.js`** (`npm run auto-version`) — All-in-one script that bumps version, updates changelog, runs quality gates, commits, pushes, and sends notification. Sends both success and failure notifications.

:::note
Neither script is called from GitHub Actions CI. They must be run manually (or wired into a custom workflow). If the notification token is not configured, both scripts gracefully skip the notification.
:::

### Notification Flow

```
Script (manual) → Notification Payload → Ingest Endpoint → notification_events table
```

```json

  "category": "deployment",
  "status": "active",
  "tags": ["deployment", "production", "success", "feat"],
  "version": "8.2.2",
  "release": {
    "version": "8.2.2",
    "environment": "production",
    "status": "success",
    "summary": "New analytics dashboard",
    "deployedBy": "developer",
    "deploymentUrl": "https://sjrslms.in",
    "commitType": "feat",
    "commitHash": "a1b2c3d",

  }

```

### Database Table: `notification_events`

The notification is saved to the `notification_events` table with:

- **title**: Summary of changes (from changelog or commit subject)
- **message**: Detailed deployment info with version, commit type, changelog sections
- **category**: `deployment`
- **version**: Version number (e.g., "8.2.2")
- **release**: Object with version, environment, status, deployer, URL, commit info
- **metadata**: Full pipeline details including changelog and commit info (JSON)
- **tags**: `["deployment", "production", "success", "<commitType>"]`
- **status**: `active`

### Verification

After sending a notification, you can verify it was saved:

```sql
SELECT * FROM notification_events 
WHERE category = 'deployment' 
ORDER BY created_at DESC 
LIMIT 1;
```

Or check via API:

```bash
GET /api/v1/notifications/events?category=deployment&limit=1
```

## Configuration

### Notification Token

For notifications to work, set one of these environment variables (checked in order):

```bash
NOTIFICATION_INGEST_TOKEN_RELEASE=your_token_here
# OR
NOTIFICATION_INGEST_TOKEN=your_token_here
# OR
RELEASE_NOTIFICATION_TOKEN=your_token_here
# OR
NOTIFICATION_EVENTS_TOKEN=your_token_here
```

If running locally, set these in `.env`. If running in CI, set in GitHub → Repository → Settings → Secrets and variables → Actions.

:::note
If no token is configured, both `notify-deployment.js` and `auto-version.js` will skip the notification gracefully — the deployment/release is not affected.
:::

### Ingest Endpoint

The notification endpoint defaults to:
- **`notify-deployment.js`**: `https://sjrslms.in/api/v1/notifications/events/ingest`
- **`auto-version.js`**: `https://sjrslms.in/api/v1/notifications/events/ingest`

Can be overridden via environment variables (checked in order):

```bash
NOTIFICATION_INGEST_ENDPOINT=https://sjrslms.in/api/v1/notifications/events/ingest
# OR
RELEASE_NOTIFICATION_ENDPOINT=...
# OR
NOTIFICATION_EVENTS_ENDPOINT=...
```

The `auto-version.js` script also supports base-URL env vars (`NOTIFICATION_INGEST_BASE_URL`, `API_BASE_URL`, `VITE_API_BASE_URL`, `FRONTEND_URL`) and automatically appends `/api/v1/notifications/events/ingest`.

### Versioning Tooling

The sjrslms app uses a **custom `version-prepare.js`** script (not `standard-version`). Key differences:

- Custom commit classification logic (not driven by `.versionrc`)
- Groups commits into 4 sections: Added, Fixed, Changed, Technical
- Supports `--skip.tag`, `--skip.commit` flags (used by CI)
- Runs quality gates locally before pushing (in local mode)
- Creates `[skip ci]` commits to prevent CI from re-triggering

The `.versionrc` file exists but is used by the `commit-and-tag-version` package (for the docs site release workflow), not by the sjrslms app's versioning.

## Version Synchronization Checklist

### Before Running `npm run version:prepare`

- [ ] All changes committed using conventional commit format (`feat:`, `fix:`, `chore:`, etc.)
- [ ] No uncommitted changes (or they'll be included in version bump)
- [ ] On `main` branch (release flow is designed around main)

### After Version Preparation

- [ ] Version in `package.json` matches git tag
- [ ] Git tag exists: `git tag | grep v8.2.2`
- [ ] Tag pushed to GitHub: Check GitHub tags page
- [ ] Quality gates passed locally

### After CI Release (Path 2)

- [ ] GitHub Actions CI completed successfully
- [ ] GitHub Release created: Check releases page
- [ ] Release version matches package.json version

### After Manual Deployment

- [ ] Deployed successfully: `npm run deploy:production`
- [ ] (Optional) Notification sent: `npm run notify-deployment`
- [ ] Notification saved to database: Check notification_events table

## Troubleshooting

### Version Mismatch

**Issue**: Tag version doesn't match package.json version

**Solution**:
```bash
# Check current version
node -p "require('./package.json').version"

# Check git tags
git tag | tail -5

# If mismatch, fix package.json and recreate tag
npm version 8.2.2 --no-git-tag-version
git tag -d v8.2.2
git tag v8.2.2
git push origin v8.2.2 --force
```

### No Version Bump on CI

**Issue**: CI `release` job runs but doesn't create a new version

**Check**:
1. Were there conventional commits (`feat:`, `fix:`, etc.) since the last tag?
2. Were all commits `chore(release):` or `[skip ci]` (these are skipped)?
3. Check CI logs for "Version unchanged" message

### Notification Not Saved

**Issue**: Notification not appearing in database

**Check**:
1. Token configured? (`NOTIFICATION_INGEST_TOKEN_RELEASE` or `NOTIFICATION_INGEST_TOKEN`)
2. Ingest endpoint accessible?
3. Script output shows "skipping database notification" (token not set)
4. Verify HTTP status code (should be 200 or 201)

**Debug**:
```bash
# Check notification endpoint
curl -X POST https://sjrslms.in/api/v1/notifications/events/ingest \
  -H "Content-Type: application/json" \
  -H "x-notification-ingest-token: YOUR_TOKEN" \
  -d '{"source":"release:pipeline","title":"Test","message":"Test","category":"deployment"}'
```

### GitHub Release Not Created

**Issue**: Release not appearing on GitHub

**Check**:
1. Tag was pushed? `git ls-remote --tags origin`
2. GitHub Actions `release` job completed successfully?
3. Check workflow logs for `github-release` job
4. Verify tag format: `v8.2.2` (not `8.2.2`)
5. The `github-release` job only runs if the `release` job outputs `released=true`
