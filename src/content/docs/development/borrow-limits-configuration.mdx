## Database Schema Changes

### Migration Required
The backend requires a migration to update the `borrow_limits` table:
- `sql/migrations/update-borrow-limits-schema.sql`

### New Schema
```sql
CREATE TABLE borrow_limits (
  user_type VARCHAR(20) PRIMARY KEY
    CHECK (user_type IN ('Student_1','Student_2','Student_3','Student_4','Professor','Guest')),
  max_books INTEGER NOT NULL CHECK (max_books > 0),
  loan_period_days INTEGER NOT NULL CHECK (loan_period_days > 0),
  max_renewals INTEGER NOT NULL CHECK (max_renewals >= 0),
  fine_per_day DECIMAL(10,2) NOT NULL CHECK (fine_per_day >= 0),
  is_active BOOLEAN DEFAULT TRUE,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

## Validation Rules
Input guardrails are defined as `BORROW_LIMIT_BOUNDS` in `shared/types/borrow-limits.ts` (shared by the admin form and backend Zod schemas):
- **Max Books**: 1–100
- **Loan Period**: 1–365 days
- **Max Renewals**: 0–10
- **Fine per Day**: ₹0–100

## User Types Supported
Per-user-type limits (max books, loan period, renewals, fine/day) are **configured in the `borrow_limits` table**, not hardcoded. Rows exist for the institution's user types (e.g., students by year, professors, guests) — manage them via the superuser dashboard at `/dashboard/borrow-limits`.

## Fallback Values

`BORROW_LIMIT_FALLBACK` in `shared/types/borrow-limits.ts` is the single last-resort fallback used when the `borrow_limits` table has no row for a user type. It is **generic** (same for every user type) — per-user-type defaults must live in the database, not in code:

- **Max Books**: 3
- **Loan Period**: 14 days
- **Max Renewals**: 2
- **Fine per Day**: ₹0.00

Both backend (`getBorrowLimitsForUser`, orders, reservations, overdue-penalty calculation) and frontend consumers import the same constant so every layer agrees on the no-row behavior.

### Fallback Behavior

1. **Database First**: System fetches limits from the `borrow_limits` table for the user type
2. **Generic Fallback**: If no row exists, `BORROW_LIMIT_FALLBACK` applies
3. **Override Anytime**: A database row always takes precedence when configured

**Important**: The `borrow_limits` table is also the single source of truth for **fine rates** — the overdue-penalty calculator and reminder emails read `fine_per_day` from it (the old hardcoded ₹25/day fallback was removed in v8.12.0).
