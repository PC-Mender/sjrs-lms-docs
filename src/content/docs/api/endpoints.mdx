This document provides comprehensive documentation for all SJRS LMS API endpoints, organized by resource type and functionality.

:::note
All API routes use the `/api/v1/` prefix. The main request pipeline normalizes `/api/v1/<resource>` to `/api/<resource>` before route matching. Legacy `/api/<resource>` paths (without `v1/`) are rejected with HTTP 400. See [API Versioning](/architecture/api-versioning) for details.
:::

## Authentication Endpoints

### User Authentication
- **POST** `/api/v1/auth/login` - User login
- **POST** `/api/v1/auth/register` - User registration
- **POST** `/api/v1/auth/logout` - User logout
- **GET** `/api/v1/auth/me` - Get current user profile
- **PUT** `/api/v1/auth/profile` - Update user profile
- **PUT** `/api/v1/auth/change-password` - Change user password
- **GET** `/api/v1/auth/check-email` - Check if email is usable (enumeration-safe)

### Email Confirmation
- **POST** `/api/v1/auth/confirm-email` - Confirm email address
- **POST** `/api/v1/auth/complete-profile` - Complete user profile setup
- **POST** `/api/v1/auth/resend-confirmation` - Resend confirmation email

### Password Management
- **POST** `/api/v1/auth/password-reset` - Request password reset
- **POST** `/api/v1/auth/validate-reset-token` - Validate reset token
- **POST** `/api/v1/auth/confirm-reset-password` - Confirm password reset
  - *Note: Requires `recoveryCode` if MFA is enabled on the account.*
- **POST** `/api/v1/auth/reset-user-password` - Admin reset user password

### Multi-Factor Authentication
- **POST** `/api/v1/auth/mfa/setup` - Setup MFA for user
- **POST** `/api/v1/auth/mfa/verify` - Verify and enable MFA
- **POST** `/api/v1/auth/mfa/disable` - Disable MFA
- **GET** `/api/v1/auth/mfa/status` - Get MFA status
- **POST** `/api/v1/auth/mfa/challenge/verify` - Verify TOTP/Backup code
- **POST** `/api/v1/auth/mfa/backup-codes/regenerate` - Regenerate backup codes

### WebAuthn / Passkeys
- **POST** `/api/v1/auth/webauthn/register/begin` - Start Passkey registration
- **POST** `/api/v1/auth/webauthn/register/finish` - Complete Passkey registration
- **POST** `/api/v1/auth/mfa/challenge/webauthn/begin` - Start Passkey authentication
- **POST** `/api/v1/auth/mfa/challenge/webauthn/finish` - Complete Passkey authentication
- **POST** `/api/v1/auth/webauthn/credentials/revoke` - Revoke a Passkey
- **POST** `/api/v1/auth/webauthn/credentials/revoke/send-otp` - Send OTP for revocation

### Session Management
- **GET** `/api/v1/auth/sessions` - Get user sessions
- **POST** `/api/v1/auth/sessions/terminate` - Terminate specific session
- **POST** `/api/v1/auth/sessions/terminate-all` - Terminate all user sessions
- **POST** `/api/v1/auth/sessions/cleanup` - Cleanup expired sessions (admin)
- **GET** `/api/v1/auth/validate-session` - Validate current session
- **POST** `/api/v1/auth/force-deactivate-sessions` - Force deactivate sessions
- **POST** `/api/v1/auth/force-logout-other-sessions` - Force logout other sessions

### Public Status Check
- **POST** `/api/v1/auth/check-status/send-otp` - Send OTP to check account status
- **POST** `/api/v1/auth/check-status/verify` - Verify OTP and return workflow status

- **POST** `/api/v1/badges/assign` - Assign badge to user - Requires `badges:create` permission
  - Body: `user_id`, `badge_key`, `reason` (optional), `expires_at` (optional, ISO datetime)
- **POST** `/api/v1/badges/revoke` - Revoke badge from user - Requires `badges:delete` permission
  - Body: `user_id`, `badge_key`, `reason` (optional)

**Security Features:**
- Prevents self-assignment
- Blocks manual assignment/revocation of role-based badges
- Requires superuser for badges with level >= 5
- Validates expiration dates
- Comprehensive audit logging

###  RBAC Policy: Backend Permission Endpoint is Single Source of Truth

**The backend permissions endpoint (`GET /api/v1/permissions/check`) is the single source of truth for all permission decisions.**

- **Backend Authority**: All permission checks must ultimately be validated by the backend `/api/v1/permissions/check` endpoint
- **Client Fallbacks**: Client-side permission checks are for UI optimization only and **deny by default** when backend validation is unavailable
- **Security First**: Never trust client-side permission checks alone - always validate on the backend
- **Fail-Safe Design**: If the backend endpoint is unreachable or returns an error, the client should deny access
